# Worktree environment parity: shadow detection, PYTHONPATH pin, and `.ap-provision` for detached runs

_Design topic (verbatim, from `/ap:design`, 2026-09-02, run issue #206):_ worktree-run provisioning for ap jobs: a detached quick/implement run works in .ap/worktrees/<topic>, and five 2026-09-01..02 forensics issues (#183, #196, #197, #190, #193) show two ways that worktree silently diverges from the checkout the brief was measured on. (a) A site-packages .pth (e.g. ~/.local/lib/python3.12/site-packages/iriscortex-src.pth on XJP-2card-A10) resolves to the MAIN checkout, so every python in the worktree, torchrun children included, imports main-checkout code unless PYTHONPATH pins the worktree; a hub probe that 'import'-checks a native extension then reports it built when the worktree has none (#197 parked a worker on exactly that). (b) Gitignored native build products (cppops .so, cc3d/edt .so built by setup.py build_ext --inplace) exist only in the main checkout, so a fresh worktree fails the gate until the hub hand-copies them (#193) or the brief carries a rebuild preamble (#190). Design what ap itself should do at job start (src/commands/job.ts worktree creation, src/core/gitwork.ts) and in the worker/hub identity: detect a .pth that resolves into the origin checkout and refuse or warn with the exact PYTHONPATH pin; provision a repo-declared list of gitignored artifacts into the worktree (copy or hardlink, like the existing node_modules hardlink clone in job start); and lint briefs that assert an environment fact from an import probe. Single-repo, no new provider, keep the frozen protocol; decide refuse-vs-warn, where the declaration lives (.ap/provision list vs a CLAUDE.md convention), and what the acceptance test is.

## Problem

A detached `/ap:quick` or `/ap:implement` run is briefed from measurements taken in the operator's main checkout and executed in `.ap/worktrees/<topic>`, which `startWorktree` creates as a fresh checkout of committed HEAD plus a `cp -al` clone of `node_modules` and nothing else (`/home/liupan/Aerius/agglomeration-platform/src/commands/job.ts:214-237`). The brief tells the hub exactly that: "That directory is a FRESH checkout of the committed HEAD the run forked from, plus a clone of node_modules. Nothing else came across: no build products…" (`/home/liupan/Aerius/agglomeration-platform/src/core/job.ts:517-520`). Five field issues from 2026-09-01 show the isolation that promise implies is not real on a Python repo, in two directions.

**(a) The worktree is not what python imports.** A user-site path-configuration file injects the MAIN checkout into every interpreter on the box: `~/.local/lib/python3.12/site-packages/iriscortex-src.pth` [on-box] — "injects the MAIN checkout into every python on this box — torchrun children of worktree pytest runs import main-checkout iriscortex unless PYTHONPATH pins the worktree" (issue #183 hub flag, issue #183); "torchrun children of worktree pytest runs silently import the wrong tree" (#183). A second shape of the same family is live on this box and I read it directly: `/home/liupan/.local/lib/python3.12/site-packages/__editable__.iris_runtime-0.1.0.pth` [on-box] is an exec-only line, and its sibling `/home/liupan/.local/lib/python3.12/site-packages/__editable___iris_runtime_0_1_0_finder.py:9` [on-box] carries `MAPPING: dict[str, str] = {'irisruntime': '/home/liupan/Iris/iris-runtime/irisruntime'}` — the MAIN checkout, with a live ap worktree beside it the install knows nothing about (`ls -la` on both files, and `sed -n 9p` on the finder, run this session). The failure is intermittent by construction: `sys.path[0]` is the *script's* directory, so a script under a worktree subdirectory resolves to the main checkout while `python -c` from the worktree root resolves correctly — an interactive spot-check passes and the real training script fails. Cost in the field: "Every scratch mutation this run had to pin PYTHONPATH to survive it, and the one GPU-leg failure was initially misattributable because of it" (#183). The same family fooled the hub in the other direction: it probed `import irisruntime.utils.cppops`, which succeeds on the package `__init__` with the extension modules absent, and wrote "the .so is already built here" into the brief; the worker parked a question and was right (#197, #197).

**Both of the failure's consumers are unpinned today, not just the worker.** The hub itself runs the gate INSIDE the worktree: `implement verify-tests` shells out with `cwd` and no `env` option (`/home/liupan/Aerius/agglomeration-platform/src/core/implementVerifyTests.ts:84-95`, "runs the TARGET repo's OWN test command in `TARGET_CWD` … in place", `/home/liupan/Aerius/agglomeration-platform/commands/implement.md:451`), and quick's hub runs `TEST_CMD` "once in `<TARGET>` via Bash" (`/home/liupan/Aerius/agglomeration-platform/commands/quick.md:305-306`). That is where #183's harm actually landed. Any fix that pins only the worker pane leaves the verification path shadowed.

**(b) The artifacts the gate needs are gitignored, so `git worktree add` never brings them.** `irisruntime/utils/cppops/` cc3d and edt are built by `setup.py build_ext --inplace` and are gitignored, so "they never cross into a fresh ap worktree" (#197, #197); "native cc3d/edt .so files are absent from this worktree; importing irisruntime.utils.cppops.cc3d fails despite the inbox stating cppops is already built here" (#197). Four remedies were improvised in nine hours: hub hand-copied the binaries, "removing two likely wasted worker rounds" (#193); hub wrote a `build_ext --inplace` preamble into the brief and "the gate ran green first try" (#190); the worker detected the absence and self-built unprompted (#196); the hub rebuilt after its own brief lied (#197). One neighbouring remedy is destructive — `pip install -e .` from a worktree re-points the operator's user-site editable finder at a directory teardown deletes, "this has bitten twice today" (#196, #197) — and is defended today only by prose in a topic string.

ap has zero handling for any of it: `grep -rl "\.pth\|PYTHONPATH\|build_ext\|site-packages"` over `/home/liupan/Aerius/agglomeration-platform/src`, `/commands`, `/config` returns 0 files. The single explicit ask in the five issues is #183's: "Worktree-based runs on a box with a src.pth are a standing trap — worth a preflight check in ap itself" (#183).

## Goal

A detached worktree run — and the hub that verifies it — imports the worktree's own tree, or the operator and the hub are told exactly what is shadowed and what is missing, before hours are spent.

Concretely, after this change:

1. **The pin is mechanical, at every place ap chooses a cwd.** When something on the box resolves this repo from the MAIN checkout, one derivation (`pythonPin`) produces one string, applied at three points: the WORKER pane's launch (`ap spawn`), the hub's own independent test re-run (`runBounded`), and — for quick, whose gate run is the hub's own Bash — the pin rendered verbatim in the brief with the instruction to prefix it. PYTHONPATH is the only mechanism that survives every hop a real job crosses: torchrun's subprocess handler does `env_vars = os.environ.copy()` (`/usr/local/Python-3.12.11/lib/python3.12/site-packages/torch/distributed/elastic/multiprocessing/subprocess_handler/subprocess_handler.py:49-51` [on-box]) and never touches PYTHONPATH, while a parent-side `sys.path.insert` dies at the Popen boundary.
2. **The brief stops lying and stops inviting the fooled probe.** The WORKTREE paragraph names the shadow and the pin, carries the pin INSIDE the probe rule (a probe with cwd in the worktree but no pin still answers about the main checkout), states the one thing the pin does not fix (an editable finder still serves a file the worktree lacks from the main tree), forbids `pip install -e` from the worktree, and — when nothing was provisioned — names the durable fix so the run that gets bitten arms the repo for the next one.
3. **Teardown can no longer break the operator's environment.** `job stop` refuses to delete a worktree an editable install — or an exec `.pth` line that names the worktree — now resolves into, and prints the repair that fits the hit (`pip install -e .` from the main checkout for an editable install; edit the named file for an exec line).
4. **A repo can declare its gitignored artifacts once** (PR B, sequenced behind the dogfood of 1-3): a committed `.ap-provision` at the repo root lists git pathspecs and `job start` COPIES the matching ignored files in, replacing the #193 hand-copy. It is opt-in; the default answer to a missing build product stays "rebuild it in the worktree", which is what the field already did successfully twice unaided (#190, #196).

Non-goals, stated so they are not re-raised: ap runs no python and no build command; no new verb, no new rc, no new refusal, no new event name, no brief-lint class, no forensics flag, no `env:` on a child process, no tmux `-e`, no configurability beyond the one opt-in declaration file. `--no-worktree` runs, panes that start at the repo root, and any box with no shadow and no `.ap-provision` are byte-identical to 0.5.65.

## Architecture

**A1 — One new pure module, `src/core/provision.ts`; no I/O beyond `fs` and an injected `Runner`, and never an interpreter.**

`shadowHits(root, home, env)`: `Array<{ source: string; importRoot: string | null }>`. Site dirs scanned: `<d>/lib/python*/site-packages` for `d` in `env.VIRTUAL_ENV`, `env.CONDA_PREFIX`, `<home>/.local`, discovered with `readdirSync` + a `python` prefix filter, every read in a `try` so an unreadable dir is silence. `home` and `env` are parameters (defaults `homedir()` / `process.env`) — the repo's own convention for an injectable environment (`/home/liupan/Aerius/agglomeration-platform/src/core/deps.ts:29`, `/home/liupan/Aerius/agglomeration-platform/src/commands/send.ts:13`) — and they are threaded through `startWorktree` and the spawn path so tests never mutate `process.env.HOME`, which would also flip `wrapLaunch`'s default (`/home/liupan/Aerius/agglomeration-platform/src/core/tmux.ts:181`).

Two signals produce a PIN, one produces a WARN only:
- a `*.pth` line that is not blank, not `#` and not `import `/`import\t`, resolved against the site dir; a hit when it equals `root` or starts with `root + "/"`. `importRoot` = that directory. This is the hand-written `iriscortex-src.pth` case and the setuptools *simple* (src-layout) case, where the `.pth` already names the import root.
- a `__editable___*_finder.py`'s `MAPPING` line: run the already-exported `pathTokensFrom` (`/home/liupan/Aerius/agglomeration-platform/src/core/implementScope.ts:89-105`) over that ONE line — its trims turn the live `MAPPING: dict[str, str] = {'irisruntime': '/home/liupan/Iris/iris-runtime/irisruntime'}` into the bare path — and for each value under `root`, `importRoot` = `dirname(value)`. The `NAMESPACES` entries are deliberately not read: subdirectories of the same tree, no new import root.
- **`importRoot: null` (warn, never pin): an `import …` exec line in a `*.pth` that no parsed finder in the same site dir accounts for.** A hand-rolled `import sys; sys.path.insert(0, '<main checkout>')` is exactly the idiom #183 describes and it cannot be resolved textually; the detection recipe this design is built on reports that class unconditionally for the same reason. Silence there would let #183 replay with ap saying nothing. The ordinary setuptools exec line, whose sibling finder WAS parsed, is not warned about.

Two refinements shipped with PR A after review, so the detector as built is narrower than the bullets above in exactly these ways: (i) every signal additionally requires the resolved path to lie OUTSIDE the prefix that owns the site dir it was read from (`VIRTUAL_ENV` / `CONDA_PREFIX` / `<home>/.local` / a teardown extra, normalised once) — `python -m venv .venv` puts the site dir under the root, and its own relative entries (`.`, `./x.egg`) would otherwise read as shadows of the checkout they sit in; (ii) the warn-only exec-line class is reported only when the line names a path under the root as a bounded substring (the root, optionally followed by `/…`, ended by a quote, bracket, comma, semicolon, whitespace or end of line — so `sys.path.append('<root>')` and `sys.path.insert(0,'<root>')` are caught and `<root>-old` is not), never unconditionally: setuptools' `distutils-precedence.pth` and virtualenv's `_virtualenv.pth` are exec-only, finder-less and present in every venv, and an unconditional warn would have broken Success Criterion 1's silence on every run.

Dropped from the earlier draft: PEP 610 `direct_url.json`. It names a PROJECT root, not an import root — the one thing the pin needs — so it can only add a wrong pin entry, and both live shapes on this box are already covered by the two signals above. Removing it also removes a full `*.dist-info` walk per spawn.

`ponytail:` ceilings to record in the module: system site dirs are not scanned and no interpreter is consulted (upgrade path: ask the job's own interpreter for `site.getsitepackages()`, which costs a python subprocess ap does not have); a PEP 660 backend that inserts its finder at `sys.meta_path[0]` and writes no plain `.pth` is invisible; and PYTHONPATH precedes the stdlib, so a pinned import root holding a stdlib-colliding top-level name (`types.py`, `select.py`) shadows it for every interpreter in that pane — checked clean for the dogfood repo (`python3` over `/home/liupan/Iris/iris-runtime` top-level importables → `['irisruntime', 'setup']`, no stdlib collision), which is why it is written down rather than discovered later. A miss anywhere here degrades to today's behaviour (no pin, no warn), the safe direction for an advisory channel.

`pythonPin(root, target, hits)`: `{ pin: string; unsafe: boolean; missing: string[] }` — maps each hit's `importRoot` onto `target` (`join(target, relative(root, importRoot))`, i.e. `target` itself when the import root IS the root), drops entries that do not exist in `target` (reported as `missing`, because PYTHONPATH silently accepts a non-existent directory), de-dupes, joins with `:`. `unsafe` is true when any entry contains `'`, `"`, `` ` ``, `$`, `\` or a newline — input validation at a trust boundary, since the pin is interpolated into a single-quoted shell word.

`pinFor(root, target, home, env)`: the ONE predicate all three application sites share — returns `""` unless `worktreeProvenanced(target, root)` (`/home/liupan/Aerius/agglomeration-platform/src/core/job.ts:68-70`) AND `shadowHits` returned a pinnable hit AND `pythonPin` is safe. The provenance gate matters: `spawn --cwd` is validated only as "an existing absolute path" (`/home/liupan/Aerius/agglomeration-platform/src/commands/spawn.ts:219`), so an attached `--target` at an unrelated checkout must not have this repo's re-rooted import path injected ahead of its stdlib. Unpinned is today's behaviour and the safe direction.

**A2 — WARN and PIN, never refuse.** A shadow is a standing property of the operator's box, present on every run there, and it is now repaired mechanically. `startWorktree` refuses only over collisions unfixable in place (`src/commands/job.ts:196-206`) and `refuseInvisibleDoc` over the one input the run exists to consume (`src/commands/job.ts:352-384`, rc 2). The matching precedent is the dirty main tree, explicitly rejected as a launch gate because "unrelated WIP is the normal state of a checkout" (`/home/liupan/Aerius/agglomeration-platform/docs/superpowers/specs/2026-08-23-worktree-truth-telling-design.md:112`). It passes the differential test: no shadow, no `.ap-provision` → complete silence (verified: no `*.pth` and no finder under `/home/liupan/.local/lib/python3.12/site-packages` [on-box] names this repo).

**A3 — The pin is applied at all three cwd-choosing sites, from one derivation.**
- **Worker pane** — `/home/liupan/Aerius/agglomeration-platform/src/commands/spawn.ts:261-262`: `wrapLaunch([binary, ...modeArgs].join(" "), undefined, pinFor(repoRoot(), startDir, ...))` → `bash -ic 'export PYTHONPATH="<pin>${PYTHONPATH:+:$PYTHONPATH}"; exec <launch>'`, prepended (PYTHONPATH is left-to-right; a stale earlier entry naming the main checkout would otherwise win), and `bash -c '…'` when `~/.bashrc` is absent because the `${VAR:+…}` expansion needs a shell. Empty prefix ⇒ byte-identical to today's two outputs (`src/core/tmux.ts:181-183`, pinned at `/home/liupan/Aerius/agglomeration-platform/tests/tmux.test.ts:42-44`).
- **The hub's own gate re-run** — `/home/liupan/Aerius/agglomeration-platform/src/core/implementVerifyTests.ts:84-95`: `runBounded` gains a `pin = ""` parameter and composes `export PYTHONPATH="<pin>${PYTHONPATH:+:$PYTHONPATH}"; <testCmd> 2>&1`; `liveTestRunner` (`:105-110`) computes it with `pinFor(repoRoot(), cwd, …)`. This is the fix for the blocking gap: the hub pane is deliberately NOT pinned (it is spawned `--cwd root`, `src/commands/job.ts:467`, and a pane-wide pin would follow it into the main checkout), so the pin must ride the one child process whose cwd ap chooses. Injected `TestRunner` fakes in `/home/liupan/Aerius/agglomeration-platform/tests/implement-verify-tests.test.ts` are unaffected; the composition is tested through an exported pure `verifyScript(testCmd, pin)`.
- **quick's hub gate run** — `/home/liupan/Aerius/agglomeration-platform/commands/quick.md:305-306` runs `TEST_CMD` in `<TARGET>` with the hub's own Bash, which no ap code wraps. The brief's shadow block renders the pin verbatim and Stage 2 says to prefix it on that run and on every environment probe. Named ceiling: an ATTACHED quick run has no `job start` to compute a pin, so there the rule is prose only.

**A4 — The probe rule carries the pin, and its limit.** #197's lesson ("a package-level import is not evidence that its extensions exist", #197) is necessary but not sufficient: on a src-layout shadow — #183's exact shape — a probe run with cwd in the worktree STILL resolves the package from the main checkout, so the hub can re-write the same false claim. The shipped sentence is therefore `PYTHONPATH=<pin> python3 -c 'from pkg.ext import sym'` with cwd in the worktree, with `<pin>` substituted from the run's own shadow block and the prefix simply absent on a clean box. One further sentence states what the pin does NOT buy: a hook-strategy editable finder delegates `parent in MAPPING` to `PathFinder.find_spec(fullname, path=[MAPPING[parent]])` (`/home/liupan/.local/lib/python3.12/site-packages/__editable___iris_runtime_0_1_0_finder.py:24-26` [on-box]), so a submodule the worktree LACKS is silently served from the main tree — verify a compiled extension by its own path under the worktree, not by the fact that an import succeeded.

**A5 — Both findings ride the job record; the brief is the hub's only channel.** `job start`'s stderr reaches the OPERATOR; a detached hub is a tmux pane whose only input is `jobBrief` (`/home/liupan/Aerius/agglomeration-platform/src/core/job.ts:526-563`). `JobRecord` (`src/core/job.ts:28-55`) gains `python_shadow?: string[]`, `python_pin?: string` and (PR B) `provisioned?: string[]`. **The keys are omitted when empty, not written as `[]`** — `formatJob` is `JSON.stringify` (`src/core/job.ts:190`), so an always-present key would change every clean-box `job.json` and break the round-trip assertion at `/home/liupan/Aerius/agglomeration-platform/tests/job.test.ts:18` against a `REC` (`:6-13`) that declares no such field. `parseJob` (`:194-224`) reads each as a string-only array (elements filtered by `typeof`) and sets the key only when non-empty, so an older or torn record still parses and no consumer is handed a non-string. No frozen name is touched: the frozen JSON fields are outbox event fields, not job-record keys. The stdout KV block (`src/commands/job.ts:472-475`) is unchanged — a machine-read contract with no reader for these.

**A6 — `worktreeLines` renders it, branching so the clean case is byte-identical.** Unconditionally, every worktree brief gains (i) the A4 probe rule and (ii) the `pip install -e` prohibition with its reason. With `python_shadow` non-empty, a block names each source, prints the pasteable `export PYTHONPATH=…`, says ap already pinned the worker pane and the hub's `verify-tests` re-run, tells a quick hub to prefix it on its own gate run, notes `sys.path[0]` is the SCRIPT's directory, and carries the split-package caveat. With `provisioned` empty (always, until PR B is armed for that repo) the existing sentence at `src/core/job.ts:517-520` is emitted unchanged — so the five literal assertions at `/home/liupan/Aerius/agglomeration-platform/tests/job.test.ts:309-313` keep asserting untouched — plus one clause naming the durable fix: if the run finds a needed gitignored artifact missing, rebuild it here with the repo's own build command, and the lasting repair is a committed `.ap-provision` at the repo root listing its pathspecs, which the hub should say in its handoff. That clause is what makes provisioning ever get armed: the run that gets bitten arms the repo for the next one. With `provisioned` non-empty the sentence is replaced by the honest one — fork + `node_modules` + the N declared artifacts, listed — plus a line saying they were built from MAIN sources and must be rebuilt here if the run touches that extension.

**A7 — The hub is disarmed by identity text, not a lint class or a verb.** An environment claim carries no path token, so `pathTokensFrom` — the single extractor all three brief-lint classes filter (`src/commands/quick.ts:203-216`) — cannot see the founding case while firing on innocent prose, against the repo's own rule that a lint must be a differential (`docs/superpowers/specs/2026-08-23-worktree-truth-telling-design.md:66-71`); a new class must also be appended after `CONSTRAINT_RELATIVE` because the record's adjacency is asserted literally at `/home/liupan/Aerius/agglomeration-platform/tests/quick-cmd.test.ts:1216-1218`. A verb would have to choose an interpreter and run python. The truth-telling spec routes hub-actor rules into `worktreeLines` (`:99-101`), but that is empty for `--no-worktree` and never rendered for an ATTACHED run — so the same rule also ships as one bullet in the citation-rule block of `commands/quick.md:144-163` and one sentence appended to the environment-asymmetry paragraph of `commands/implement.md:478-484`.

**A8 — No forensics flag.** Only a class that can never be correct files one (`src/commands/quick.ts:188-192`). A box-wide editable install is legitimate and standing; flagging it would file an issue on every run on that box forever. A run that is actually bitten still files a hub flag by hand, as #183 and #197 did.

**A9 — Teardown keeps a worktree an editable install now points into.** `sweepWorktree` already keeps a dirty worktree (`/home/liupan/Aerius/agglomeration-platform/src/commands/job.ts:293-296`). Before `git worktree remove` (`:298`) it calls `shadowHits(wt, …)` with the site-dir set WIDENED for teardown only — additionally `<root>/.venv`, `<root>/venv`, `<worktree>/.venv` — and if anything now resolves INTO the worktree, keeps it, names the source and prints `cd <root> && pip install -e .`. Stated ceiling, in the spec and in the brief: this is best-effort — the worker pane is `bash -ic` and may have activated a venv the stopping process never saw — so the brief prohibition stays load-bearing rather than being demoted to a backstop. Rejected as a widening: keeping on the presence of an unprovisioned `*.egg-info`. `setup.py build_ext --inplace` produces one as a normal byproduct (the live worktree at `/home/liupan/Iris/iris-runtime/.ap/worktrees/implement-phases-f-g` carries its own `build/` and `iris_runtime.egg-info/` with inodes distinct from main's), so that condition would keep every python worktree forever and train the operator to force-remove.

**A10 — Placement.** The detector call and (PR B) provisioning live inside `startWorktree` (`src/commands/job.ts:188-253`), in the slot the `node_modules` clone occupies between the fail-closed `git worktree add` (`:214-218`) and the dirty-tree warning (`:238`). That inherits the existing real-git test harness and makes `--no-worktree` correct by construction (`src/commands/job.ts:446`). The return widens to `{ worktree, baseSha, shadows, pin, provisioned }` and `startRun` copies them onto the record before `atomicWrite` at `:465`.

**A11 (PR B) — `.ap-provision`: opt-in, read from the MAIN checkout, enumerated per line by git, COPIED.** One repo-relative git pathspec per line; `#` and blanks skipped; a line that is absolute, starts with `-` or `:`, or contains a `..` segment is rejected with its line number (a committed file steers where files land — validation at a trust boundary). Enumeration is **one call per declared line**, not one call for all of them, because a single call cannot say which pathspec matched nothing and re-deriving that would mean re-implementing git's matcher: `git ls-files -z --others --ignored --exclude-standard -- <spec> ':(exclude)node_modules' ':(exclude).ap'`. Verified this session in a scratch repo: with the excludes, a `.` spec prints only `pkg/_ext.so` (without them it also prints `.ap/x/g.so` and `node_modules/a/f.so`); a zero-match spec prints nothing at rc 0; an invalid spec exits 128. So **rc ≠ 0 is a hard "enumeration failed — provision nothing for this line, warn"**, and empty-output-at-rc-0 is the zero-match warn naming `.ap-provision:<n>`. `runnerAt` (`/home/liupan/Aerius/agglomeration-platform/src/core/gitwork.ts:10-22`) gains an explicit `maxBuffer: 64 * 1024 * 1024` — one line, the same value `implementVerifyTests.ts:88` already uses — because it has none today and Node's 1 MiB default turns a large ignored tree into a truncated stdout returned as `{code: 1, stdout: <partial>}` (measured: `execFileSync` over 2 MB threw `ENOBUFS`, `status=null`, with 1,056,768 bytes surviving). Placement is `mkdirSync(dirname(dest), {recursive:true})` + `copyFileSync`; every placed path is NAMED on stderr in the existing 10-plus-`+N more` shape (`src/commands/job.ts:238-249`: "WHICH files, not just 'the tree is dirty'"), never a bare count — `--others --ignored` is where `.env` and credentials live, and the operator must see what crossed into a directory an autonomous TUI works in. After placement, one `git -C <worktree> check-ignore <placed…>` (verified: prints only the ignored paths, rc 0 when any match) warns for any provisioned path the WORKTREE does not consider ignored — main's working-tree `.gitignore` and the worktree's committed one can differ, and an unignored provisioned file would make `sweepWorktree` keep the worktree on every run and surface in `implement scope-check`. Every failure is non-fatal, like the `node_modules` chain (`src/commands/job.ts:235-236`). Reading the file from the MAIN checkout is load-bearing: a brand-new, still-uncommitted `.ap-provision` works on its first run, so it never joins the invisible-doc refusal class; committing it carries it to the next operator and the next box.

**A12 — COPY, never hardlink, for declared artifacts; `node_modules` keeps its `cp -al` chain.** A hardlink is not copy-on-write, so a tool that truncates in place writes through into the operator's own checkout — the one thing `worktreeLines` promises ap will not touch (`src/core/job.ts:513-514`). The field canonically runs `setup.py build_ext --inplace` inside the worktree, sometimes unprompted (#196). `node_modules` stays hardlinked: npm writes-new-then-renames, and that behaviour is shipped and argv-pinned (`/home/liupan/Aerius/agglomeration-platform/tests/job-worktree.test.ts:165`). Rebuild-by-ap is rejected outright — ap does not know the build command, a build can take hours and fail, and executing a repo-declared command at launch is a code-execution surface this codebase does not have (its only non-git, non-tmux subprocess is `cp`).
